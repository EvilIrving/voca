## 产品起点

产品研发坚决确立个人日常高频使用体验为最高优先级，坚决拒绝脱离实际场景的过度设计与宽泛妥协，全部功能细节与交互流程必须首先100%满足创作者自身最真实、最舒适的训练体验。用户觉得有道等商业口语软件体验与功能完整，但 1 年数百元的会员订阅费用过于高昂，而且模型提示词与具体规则对用户完全封闭，无法根据个人意愿定制场景与深度调优。因此优先为自身量身打造1 款顺手、流畅且完全不设会员门槛的纯客户端应用，本地服务做好之后，由用户自行接入豆包、OpenAI、Gemini 或讯飞等具备语音交互能力的模型供应商，预制标准接口转换层支持自由填入密钥。每天练习310 分钟每月仅需极低接口开支，在彻底打磨好自身体验闭环的前提下，后续顺带开源共享给具备同样痛点的社区群体。

使用者目前处于大学英语4 级水准，极度排斥死记硬背单词书和枯燥繁琐的语法条文，希望通过每天与人工智能对话练习逐步过渡到雅思6.5 分以上。针对这1 诉求，讨论确认完全不需要通过机械背诵积累词汇和语法。4 级储备的4000 多词汇已经能够覆盖日常对话90%以上的高频场景，原本属于阅读理解的被动词汇在2 至4 周的对话中即可转化为口语主动表达；雅思所需的更深层次词汇完全依托语境习得，在交流中接触新搭配并连续复现7 至12 次即可自然内化。语法同样依靠可理解性输入与即时反馈，在每轮交流末尾指出关键偏误并提供母语者地道改写和通俗解释，依靠持续输出建立语感。

用户指出目前市面上无论是语音模式还是通用对话界面，口语输入体验都极其不稳定。练习者表达英语不像表达中文能够连贯输出，在组织语言与挑选词汇时往往需要停顿思考十几秒甚至 1 分钟，然而通用实时语音依赖全自动静默检测，通常静止1 至3 秒就会误判为发言结束并立刻提前抢话，导致练习者话没讲完就被打断，严重损害口语练习体验。因此产品彻底抛弃全自动语音感应，改用手动控制开始与结束收音的回合制交互机制，给予使用者充分的思考与组织语言时间。同时系统必须支持中英混说，当遇到表达卡壳或生词匮乏时直接容许插入中文，由系统自动识别意图并给出地道的英文改写示范。

亚洲口语练习者普遍存在语调扁平、缺少抑扬顿挫以及情感感染力匮乏的现象，表达往往呈现机械背书状态。针对这1 核心体验痛点，产品在设计层面重点强化情感交互：首先促使人工智能角色具备充沛的情绪起伏、语气感叹与共情能力，通过高拟真且富有感染力的语音带动练习者进入真实自然的交谈状态；其次在界面反馈卡片中跳出单纯的词汇语法纠偏，专门设立韵律语调与情感传达建议，直观呈现升降调对比与情绪化口语表达示范；最后在主界面波形与动效设计上融入情绪感知反馈，通过视觉与听觉的深度协同，引导使用者释放情绪并建立自信舒展的母语者表达习惯。

用户认为产品开发必须先将功能与交互彻底确定，因此坚持设计前置原则，先在 Figma 中完全1:1 参照有道等优秀商业软件的成熟交互完成界面设计，然后再进入编码开发。目前指定的 [Figma 画板链接](https://www.figma.com/design/6br1NEidzHTn39lmijberV/Speaker-App?m=auto&t=2bAscD45uQknkrco-6)已经建立，后续全套界面原型与主题规范均在此持续推进。整个界面高度组件化与定制化，重点涵盖4 个主要部分：提供手动录音控件与波形动效的主对话界面、展示语法修正与母语者表达建议的折叠反馈卡片、在对话中自动提取地道搭配与例句的生词库，以及允许自由切换模型提供商、管理预设角色与自定义系统提示词的设置页。

口语交流的沉浸感高度依赖响应时延，真人自然交谈的停顿间隔通常在200 至500 毫秒之间。传统级联由于语音识别、文本生成与语音合成3 者串行累加，端到端延迟往往超过1.5 秒，容易产生明显的迟滞感；而端到端多模态语音模型跳过文本中转，配合底层流式传输协议，能够将首包音频响应时间压缩在600 至800 毫秒以内，极度贴近真实交流节奏。同时，为了避免后台复杂的语法评估与生词提取挤占主交互带宽与渲染资源，所有文本分析任务全部采用多线程异步触发机制，与主音频下发链路彻底隔离，确保使用者无论何时结束录音均能立刻获得人工智能的流式回复。

## 技术底座

用户确认彻底舍弃传统3 段式级联流程并交由后续开源社区自行补充，客户端架构完全聚焦原生多模态交互、专业发音评测与后台异步分析3 套服务商抽象。架构层面严格贯彻依赖倒置与分层隔离原则，主交互层接入端到端多模态语音模型，现接 Google Gemini Live、OpenAI Realtime 与火山引擎豆包实时语音3 家；音素级发音评分层同时对接微软 Azure Speech 与科大讯飞智能语音评测接口，支持使用者自主录入凭证并基于单次录音获取音标层面的精准分数与发音偏误；异步分析管线走一家 OpenAI 兼容的文本引擎，DeepSeek、Gemini、OpenAI、Anthropic、Kimi、GLM 与自定义端点都能接，通过结构化数据完成语法修正、地道建议和语境生词归集。状态管理贯彻单1 数据源与单向数据流动机制，将系统全部变迁收敛于确定性状态机，网络回调与主线程会话标识实施原子互斥保护；底层音频管道在读取异常时主动注销并重置句柄，播放的队列、写入线程与退出标记随每1 段播放会话各自成套，停止只作用于当前这1 段、句柄由持有它的线程释放，并接入系统音频焦点调度，平滑避让外部来电；上行音频快照跨采集线程与主线程访问时统一走同一把互斥锁；长连接在握手未就绪期间排队缓存音频帧并保留流结束标识，连接中断时引入包含随机抖动参数的指数退避重试算法；所有服务商凭证、系统提示词、聊天历史与生词库全量存储在本地数据库中，数据库严格确立版本迁移规约并保持历史记录时间戳不可变性，敏感密钥统一依托安卓安全密钥库实施硬件级加密隔离，无需任何云端服务器中转，彻底保障个人数据隐私。

针对客户端跨平台工程实现，团队深入研读了 NSGo 仓库源码。在核心音频与移动端架构层面，NSGo 存在关键技术边界：其一，在 Android 端，NSGo 采用 Java 宿主通过 ProcessBuilder 启动 Go 子进程并通过管道进行进程间通信，其 microphone_other.go 明确将实时流式录音接口 Capture 标记为不支持（直接返回 ErrUnsupported），且架构文档确认当前仅支持写入文件的离线 RecordWAV 录制，导致在 Android 端无法直接向大模型推送逐帧实时音频裸流；其二，在 iOS 端，Capture 采用 purego 动态调用 AudioToolbox 并通过 AudioQueueNewInput 获取裸流，而播放组件基于 AVPlayer 且在应用退入后台时强制暂停，缺乏针对双工低延迟交互与后台会话的完备调度；其三，官方文档自承 Android 端的录音服务与真机测试尚未完备。相比之下，Kotlin 跨平台方案在 Android 端直接在主进程调用 AudioRecord 与 AudioTrack，配合协程直接以毫秒级时间片提取裸流并双工流式推送，在 iOS 端依托 Kotlin/Native 强类型绑定直连 AVAudioEngine，2 端均具备全双工裸流实时吞吐与系统音频会话掌控能力。因此若要实现低延迟流式语音交互，NSGo 现状受限于底层管道架构与接口缺失，Kotlin 跨平台拥有无可争议的源码级依据支持。

针对原生 Android 客户端开发，采用现代技术栈（Kotlin 配合 Jetpack Compose 声明式界面）不仅完全可行，而且在核心音频链路与生态成熟度上具备极高优势。底层音频捕获与流式下发层面，Android 原生音频接口（AudioRecord 与 AudioTrack）能够直接以毫秒级缓冲区提取16 位原始音频裸流，无需经过中间文件转换，便可借助协程与长连接直接对接多模态端到端模型，同时实时计算振幅驱动波形组件的高帧率流畅渲染；服务商集成层面，微软 Azure 语音评测与各大语音厂商均提供官方原生的 Android 客户端开发包或标准流式协议库，集成调用更为直接规范；本地持久化层面，依托系统内置的本地数据库组件（如 Room）与安全存储机制，能够高标准完成敏感凭证与历史数据的离线闭环存储；该路线唯一的客观属性在于受限于单1 系统生态，若前期以个人日常主力安卓设备的高频训练为绝对重心，这属于极为扎实且确定性极高的技术方案。

若后续确定覆盖 iOS 与 Android 双端体系，采用 Kotlin 跨平台技术（Kotlin Multiplatform 结合 Compose Multiplatform）比 NSGo 具备更加压倒性的工程成熟度与确定性。Kotlin 跨平台方案获得官方深度支持，能够实现业务状态、数据持久化与流式网络管线高度共用，同时通过平台规范接口无缝桥接2 端原生音频引擎（iOS 的 AVAudioEngine 与 Android 的 AudioRecord），各大服务商原生客户端开发包均可直接对接；相比之下，NSGo 虽然具备纯 Go 语言统一代码与原生视图渲染的优势，但整体生态尚处于起步阶段，在双端毫秒级裸流双工调度与系统级音频焦点管理上仍缺乏广泛的生产验证。因此若追求兼顾双端并彻底打磨核心音频体验，Kotlin 跨平台方案显著更为稳健且具备极高的实现确定性。

仓库根目录按双端并排收：安卓 Gradle 工程进 `android/`，iOS Xcode 工程进 `ios/`，出厂提示词仍在根目录 `prompts/`，凭证仍在根目录 `.env`，画板脚本与闸门仍在 `tools/`。一对一指的是产品体验：屏幕、手势、回合、供应商、评测、生词、记忆、收段与文案必须同一份，界面上出现的每1 个字都从安卓源码抄，日志只进系统日志不进界面，也不另加空态解释、道歉提示或新的交互入口；技术选型禁止把安卓实现原样搬过来，界面用 SwiftUI，采集与播放用 AVAudioEngine，长连接用 URLSessionWebSocketTask，密钥进 Keychain，库用系统 SQLite，图标用 SF Symbols，不把 AudioRecord、OkHttp、Room、Fluent 矢量路径或自写 SVG 解析搬过去。连接4 档只在内部流转，顶栏不放圆点；进行中的会话名按安卓 `project()` 保持空着，名字只在接着聊某条历史会话时从记录带进顶栏；输入条的暂停与试听在安卓 ViewModel 与输入条里已经有，根上漏接的那截 iOS 接到根上，不把它当成新功能。

产品层仍抄安卓，工程层不允许比安卓更差：架构、界面、跟手、帧率和日常手感都要压过安卓那1 端，不能把 Compose 的刷新方式原样搬进 SwiftUI 让整屏跟着电平抖。电平、计时、波形只给输入条自己的 DisplayLink 读，不进会话列表的状态树；触控跟手用 UIKit 与 ProMotion 120 帧，列表滚动跟住尾巴时不带动效抢手。最低系统按最近2 个大版本，当前是 iOS 26，不为此照顾更旧的机型，Info.plist 打开 `CADisableMinimumFrameDurationOnPhone` 让高刷真正跑起来。这几条收在 `tools/ios-parity.sh`：高刷开关、禁搬的安卓实现名、电平不进 `@Published`、状态没变不发布、输入条不用 TimelineView，界面中文从安卓源码抽出来对。`tools/ios-gate.sh` 跑完这条再编 iOS。

结合参考截图中核心交互的视觉要求，产品涉及3 类深度定制化界面：持续触控激活的渐变弥散光晕、实时跳动的声波柱状图与上滑手势判定组件；集成发音与语法双重分值徽标的对话气泡；附带物理拖拽阻尼感、嵌套滚动与多标签平滑切换的半屏评测分析抽屉。在实现这类高度定制化且要求高帧率跟手度的动效与交互组件时，Compose Multiplatform 拥有压倒性优势，其底层的声明式画布绘制接口、手势识别指针系统与弹性动效引擎允许逐像素精准调优；相比之下，NSGo 依赖各平台系统级原生控件映射，当遭遇复杂的手势滑动拖拽、连续声波高频重绘与深度定制的弹窗动效时，难以在双端取得一致且细腻的视觉表现。因此从深度定制化界面的开发维度审视，Compose Multiplatform 属于显著更优的技术方案。

实时对话、发音评测、异步分析3 条链路各自独立成套，不追求单1 供应商覆盖全部能力：实时对话层接 OpenAI Realtime、Gemini Live 与豆包实时语音，发音评测层接微软 Azure 语音评测与讯飞语音评测流式版，异步分析层是一家 OpenAI 兼容的文本引擎，用哪家由设置页决定。客户端只认1 套内部接口，会话适配器负责连接、推送音频帧、打断、结束与事件回调，事件统一为用户语音活动、识别文本、助手文本、音频块、回合结束与错误6 类，界面只对事件流做投影，不写任何供应商分支。音频在适配层完成归1，上行统一为16 千赫兹单声道16 位小端、20 毫秒1 帧，下行统一为24 千赫兹，重采样与编解码只发生在适配器内部。每个适配器声明能力清单，涵盖是否支持打断、是否接受文本输入、是否回传流式识别、是否给出音素级分数与会话时长上限，设置页与对话页根据清单开关功能，不根据供应商名称做条件判断。1 次会话绑定1 个实时供应商，音频上下文与角色音色在会话内不替换，断线只做同一供应商的重连与上下文续接；切换模型发生在会话开始前，切换后新建会话，避开音色跳变与上下文错位。

v1beta 的 SessionResumptionConfig 只有1 个 handle 字段，续接的做法是在 setup 里带 sessionResumption.handle，服务端随后推送 sessionResumptionUpdate 给 newHandle 与 resumable，resumable 为假表示此刻不可续、旧 handle 仍对应更早的可续位置，不能清。到点换连接走另1 个入口：setup 里的 historyConfig.initialHistoryInClientContent，setupComplete 之后服务端先把 clientContent 吃到 turnComplete，这段历史不触发模型调用，所以10 分钟1 换只带压成纯文本的摘要，比带 handle 更省；突发断线才带 handle 原样续上。取消只发 activityEnd 不发 audioStreamEnd 的做法是从既有实测反推的，官方 proto 里 audio_stream_end 的注释说它只应在自动断句开启时发送，而这条链路自动断句是关的，2 条说法相左，最终以真机实测为准，代码注释里已标明这1 点。

对话列表与会话下拉都是懒加载列表配稳定 key，滚动只重组可见行；波形34 根柱在单个 Canvas 里画完并按帧计数重绘，不进组合树；下拉与半屏面板只在开合时挂载，动画只做透明度与位移、180 毫秒收尾；反复出现的文字样式在 Type 里定成常量，组合期不逐处 copy。验收按真机 `dumpsys gfxinfo` 读：滚动与录音2 段各自看总帧数、卡顿帧占比与 50、90 分位，构建通过不等于流畅。

已在 gemini-3.8-live 上跑通完整回合：WebSocket 握手加 setup 约0.9 秒收到 setupComplete；把 realtimeInputConfig.automaticActivityDetection 置为 disabled 后，开始收音发 activityStart，上行16 千赫兹单声道16 位、20 毫秒640 字节1 帧，结束收音发 audioStreamEnd 与 activityEnd，其中 audioStreamEnd 必须传布尔 true，传空对象会被服务端拒绝；activityEnd 之后约450 毫秒收到第一块音频，格式 audio/pcm;rate=24000，1 轮5 秒半语音返回5.5 秒音频，开启输入与输出转写可以直接拿到中英原文。音色由 speechConfig.voiceConfig.prebuiltVoiceConfig.voiceName 指定，Aoede 实测可用。现网可用的实时模型有 gemini-3.8-live、gemini-3.8-live-extended-thinking、gemini-3.1-flash-live-preview、gemini-2.5-flash-native-audio-latest，以及专做实时转写的 gemini-3.5-transcribe-live；文本侧默认 gemini-flash-latest，gemini-4-argon 这类进阶模型只在付费层开放。这条手动回合制链路正好对上长按说话的产品交互，自动断句关掉之后模型一直等到 activityEnd 才开口，停顿十几秒也不会被打断。

OpenAI Realtime 的 WebSocket 直连入口是 wss://api.openai.com/v1/realtime?model=gpt-realtime-2.1，当前文档的 WebSocket 示例逐字用它；wss://api.openai.com/v1/live/sessions 那条属于另1 个产品 GPT-Live，模型号 gpt-live-1.1、首条消息发 session.start、等 session.started，带 delegation 后端，与本项目用的 Realtime 不是1 回事；鉴权用 Authorization 头携带用户密钥，本项目没有服务端，按直连落地，将来接服务端时改为临时凭证。手动回合制靠把 audio.input.turn_detection 置为 null 关闭服务端断句，录音结束发 input_audio_buffer.commit 与 response.create，取消发 response.cancel 并在本地丢弃迟到的音频；输入输出都是 audio/pcm 24000，现有采集是 16k，重采样只在适配器内部进行；会话上限610 分钟，音色在首次响应后不可更换。豆包走的是 3.0 全双工版（Seeduplex），端点是 wss://openspeech.bytedance.com/api/v3/duplex/realtime/dialogue，整条链路是 JSON 文本帧：session.create 建会话，音频走 input_audio_buffer.append 的 Base64，input_audio_buffer.commit 宣告这段说完，response.cancel 打断，session.close 收场。鉴权只用1 把 API Key，走 X-Api-Key 头，官方 Go 示例的拨号代码里也只带这1 个头，实测只带这1 个头就能建起会话，session.created 在连上之后 300 毫秒左右回来。session 里 model 必传，取值只有 1.2.6.1 这1 个，上行 PCM16 16 千赫兹，下行必须在 audio.output.format 里点名 pcm_s16le 与 24 千赫兹，不点名服务端默认发32 位小端 PCM，播放链路读16 位就是噪声；音色走 audio.output.voice。上行按实时节奏发，20 毫秒 640 字节一帧，节奏偏离都会被服务端判错，所以长按期间直接透传采集帧，不攒包。回合收口要靠两条一起发：input_audio_buffer.commit 与 input_audio_mute.commit，松手时先报音频到此、再报关麦。实测只发 commit 时服务端回了 input_audio_buffer.committed 就没了下文，22 秒内不问也不答，补上关麦那一条约 550 毫秒后才出转写、再约 120 毫秒出第一块音频；所以真正让这一轮动起来的是关麦通知，commit 只把音频缓冲封口。再开口前要发 input_audio_unmute.commit，实测不发时下一轮的上行帧被服务端忽略，识别一个字都不出，发了才正常出字并作答。转写的整句在 conversation.item.input_audio_transcription.completed 的 text 字段里，delta 每一条带的都是当前整句而不是增量，所以只取 completed 那一条。取消有真正可发的动作，response.cancel 之后服务端回 response.canceled，迟到的旧内容仍按响应号在本地丢掉。转写只在 conversation.item.input_audio_transcription.completed 取1 次，界面气泡是追加语义，逐字回填会把同一句叠几遍；模型文本取 response.output_text.delta，response.output_audio.delta 的 delta 是 Base64 的裸 PCM，response.output_audio.done 当本轮收尾。历史与续接这版有了正规入口，conversation.item.create 一次能带20 轮，session.id 相当于 dialog id 可接续，现阶段仍沿用把流水接在 instructions 后面的做法。iOS 端仍是二进制帧那一版接入，还没切到这条。

端到端实时对话与异步文本分析链路中，谷歌 Gemini 综合表现完全满足高频训练需求，依托实时多模态长连接能够以数百毫秒级低延迟完成16 千赫兹双工收发与中英混说意图理解，依托其极速文本模型亦能结构化输出精准的语法偏误与地道母语者改写；然而在专业音素级发音测评层面大语言模型存在客观声学边界，生成式多模态模型仅能基于宏观音频特征给出流利度预估分值，缺乏底层基于国际音标的声学强制对齐能力，无法指出特定词汇的元音开合程度、次重音偏误或辅音缺失细节，若追求单词音标级别的严谨发音纠偏，必须保留微软 Azure 语音评测或科大讯飞等专业评测引擎处理该项声学评估，若前期主要聚焦会话流利度建立与地道语法内化，单凭 Gemini 1 套服务商便能闭环支撑核心交互。

顶栏不放任何计数，第几轮这类进度只留在记录行里，练习时不必盯着数字。会话名由异步分析链路在会话真正结束时写1 次，命名材料取整段对话而不只是开场那句，产出的是能指认内容的短语，比如没睡好的早晨、咖啡店点单，而不是新会话、练习1 这样的占位。名字在会话结束后写回顶栏中段，也在会话记录列表里露面；开新会话的那1 刻写上1 段的名字，切后台或应用被杀掉导致没写成，下次启动扫最近24 小时未命名的会话补写，最多补3 条。自动名写定即固定，界面不留改名入口，命名只由异步分析链路写1 次，会话记录列表同样不设改名，回看的地方不该做成管理界面。记录行点开就是接着那次会话继续聊，整段对话连同译文与评分原样铺开，新的轮次续在后面，续得再长也不重命名。

1 段会话由4 种时机收口：切到别的会话、点新会话、静默310 分钟、进程退出。收口时把这1 段落库、算轮次与双项均值、异步取1 次名字，然后开新的1 段；静默判定是1 枚纯函数，310 分钟内没有操作也没有在收音才收，定时器只在 ViewModel 里走，界面不自己起表。同一段只交1 次账，点新会话与静默同时到点也只落1 条记录。冷启动直接进新的1 段，历史走侧边抽屉。

抽屉里点开的每1 条旧会话都可以接着说下去：整段对话连同译文与评分原样铺回屏幕，顶栏左侧是返回箭头、中段是那1 段的名字，新的1 轮续在旧轮后面。连接按那条会话最近的1 段流水开场，从最后1 句往前数、带够2400 字，早于预算的轮次就此丢掉；Gemini 走 setup 里 historyConfig.initialHistoryInClientContent 那条原生入口，OpenAI 与豆包没有可跨连接续上的句柄，材料接在系统提示后面一起进 setup。开场那句固定问候不发，模型从这段流水接着往下说，也不复述。账本接管那条会话的标识与起点，收口时写回同一条记录：轮次与双项均值按整段重算，名字与起点保持第一次的值，中间夹着的别的会话轮次不会被圈进来；名字写定即固定，续得很长之后名字可能只概括开头那1 截。返回箭头、点新会话、静默310 分钟与进程退出都在收口后开新的1 段，退出续聊不会把那1 条留在半开状态。

手势的起点在那条360 乘120 的输入条上，贴底48 的胶囊行里右侧收着48 的圆钮，拇指按下去的位置就在屏幕底部往上48 像素这条横带里。按下先等190 毫秒分清点击与长按，点击在原地把胶囊变成草稿输入框，草稿空着时照样按住就能录、开录顺手把草稿收掉，超过190 毫秒进持续触控态：圆钮在100 毫秒里长到82、从胶囊右端剥成1 枚独立圆钮，左端浮出10 的红点与 `0:04,6` 的计时，中间留「滑动以取消」，圆钮上方16 的位置浮出36 乘56 的锁条与墨色提示气泡。左滑时可走的距离是屏宽的35%、封顶140，360 宽的屏等于126；进度 `1 + 左移 ÷ 126` 从1 走到0，归0 当刻就地作废、不用抬手，抬手时进度掉到0.45 以下也作废；圆钮按 `0.7 + 进度 × 0.3` 缩到57，位置每帧按 0.7 / 0.3 指数滤波落后手指1 截，提示跟着手指左移并按进度淡出。上滑96、且左滑进度不低于70%才能锁进锁定态，圆钮换发送箭头，暂停键在560 毫秒后浮出。暂停后胶囊左端换垃圾桶，中间那条236 乘32 的深色波形条摊开刚录下的那段，右端仍是发送，圆钮上方浮出恢复键。底栏高度由输入条自己算，64 上留、48 条身、8 下留，共120，5 个形态同高，圆钮长到82 后右缘越过屏幕9。

严禁在界面视图中直接堆砌平铺的散碎节点。在设计与未来 Compose 编码中，输入条强制统一收敛为360 乘120 的标准组件容器，内部自底向上划分为清晰独立的3 层架构：底层常驻胶囊层（Capsule_Base_Layer）承载48 高度的输入胶囊与右侧动作基底，负责常规文本编辑与基础测量，杜绝因外部动效引发的布局重排；中层手势声波光晕层（Aura_Canvas_Layer）独立挂载由触控电平驱动的双层水波纹与82 直径的核心麦克风圆球，依托画布独立绘制，保障高帧率下不挤占界面树布局；顶层浮动控制层（Floating_Controls_Layer）专职承载上滑锁扣胶囊、暂停控件与恢复控件，基于固定纵向偏移在安全边界内悬浮，消除负坐标越界风险并实现指针事件的精准隔离。画板全量真机视图统一引用该组件集实例，确保未来工程实现与设计资产严格对应。

安卓输入条的产品数字来自 VoiceGesture 与画板 164:2：190 毫秒分清点击与长按、400 毫秒双触抑制、左滑可走屏宽35%封顶140（360 宽屏等于126）、上滑96 且左滑进度不低于70%才锁、抬手进度掉到0.45 以下作废、圆钮按 0.7 加进度乘 0.3 缩放、位移每帧 0.7/0.3 跟随、暂停键延迟560 毫秒淡入、双层陶土光晕约110 与94。iOS 不得另改1 套阈值，也不把 Telegram 源码里的57 上滑、负150 作废或负400 速度锁搬进来。触控实现对齐 Telegram-iOS 的 `TGModernConversationInputMicButton`：UIControl 跟踪手指、UIPanGestureRecognizer 取速度、CADisplayLink 在长按成立后每帧把目标位移喂进 VoiceGesture 的 0.7/0.3 跟随，手指停住圆钮仍会自己追上；锁定与暂停后 overlay 卸掉，暂停、恢复、发送、取消才能点到。提示没动时原地摆3.6、500 毫秒1 趟，「滑动以取消」与「松手取消」交叉溶解160 毫秒并上下各挪12，与安卓同一套。

输入条这1 层不引入弹簧求解，位移每帧按 `current = current × 0.7 + target × 0.3` 做指数滤波，图形始终落后手指1 截、松手自己追上来；圆钮缩放直接由左滑进度推出，锁定进度直接由纵移距离除以96 推出，2 者都是当前帧的位置算出来的，不跑定时动画。实时电平按 `current × 0.9 + input × 0.1` 平滑，20 毫秒1 帧的分贝被压成呼吸，34 根柱因此不抖。阈值、曲线与平滑全部收在同一个纯 Kotlin 文件里，状态转移是1 次归约，界面只把指针事件喂进去、只投影状态，动画只负责入场退场的透明度与位移。

整屏的 pointerInput 只挂在要覆盖的那1 层的祖先上，或只在需要时挂载：同一父节点下后绘制的兄弟一旦带 pointerInput，命中测试就停在它身上，垫在下面的层1 个事件也收不到。手势循环先 awaitFirstDown 再判状态，不在 awaitEachGesture 的循环体里先看状态就 return，那1 步会去等所有手指抬起，没有手指时化成主线程上的空转。手势层的落点与按钮重叠时，读指针的那层挂成按钮的祖先，按下取 `requireUnconsumed = false`，按钮自己的 clickable 照旧管按压态与单击。侧边抽屉的横滑单独成层：排在卡片之后、抽屉之上，只在抽屉收起时存在，纵向按底栏高度让出录音带；挂在被变换的卡片里，指针坐标跟着位移与缩放一起变，挂在整屏之上，抽屉里的行与检索在命中测试里被挡住。

贴底的胶囊行在最下面，双层光晕压在胶囊之上，82 的圆钮压在光晕之上，锁条、墨色提示气泡与暂停恢复2 枚悬浮键在最上面。3 格视觉按固定坐标摆放，圆钮长大、左滑缩短、锁条抬高都不带动胶囊1 格。左滑时提示跟着手指走，位移取胶囊宽度的 1/4 乘剩余比例再叠30%圆钮位移；没动的时候在原地左右摆，幅度3.6、500 毫秒走1 趟。进度压过0.45 换「松手取消」，2 句交叉溶解、1 句上浮1 句下沉各12。锁条始终正放、收窄10%6、跟着手指往上抬，抬到40 封顶，提示气泡走过2 成就淡掉；锁定后停录键延迟560 毫秒淡入。作废先让垃圾桶动效把录音条吞下去再收，锁定态点「取消」与暂停态点垃圾桶都走这1 条。上滑行程96，拇指压在屏底时不至于蹭上去把1 轮锁成免提。

## 录音与判据

按下去没说、说得太短、或者只是键盘敲击与环境噪声，这1 轮不进实时链路也不落气泡，收尾由本地人声检测模型判频谱形状，不判音量。安卓跑 Silero VAD 的 ONNX（MIT，随包走，onnxruntime-android），iOS 用系统 SoundAnalysis 的 `SNClassifySoundRequest.version1`，2 条都不联网。送进模型前抹掉直流并按分位电平归一化到负 20 分贝，归一化做在量化之前：麦克风增益、说话远近、压着嗓子的音量差都在这1 步被抹平。参照取 32 毫秒窗 RMS 的九成分位，不取峰值：按住手机时的1 声撞击能把峰值顶到满量程，跟着峰值归一就把后面整句语音压到模型听不见的地方，判出来是零毫秒；分位参照对这1 类瞬时不敏感，语音占整段一小截时也仍落在语音上。判定看最长的1 段连续人声，不看累计帧数，零散尖峰凑得够时长也不算说话，1 句话里短于100 毫秒的换气仍算同一段。时长门槛只挡清嗓子，挡噪声靠置信度阈值；2 端的最小连续人声都是300 毫秒，帧粒度各自不同。判定排在松手之后、后台线程，新的1 次按压掐掉上1 轮判定；判掉时静默回空态，不弹提示、不落气泡、不留上行音频。

用 Silero，不用 TEN VAD：它的 ONNX 输入是声学特征加状态，特征要自带的 C 代码算，2 端都得连带移植；许可在 Apache 之上附加了不得让第三方据此开发或部署应用的条件，与开源共享的方向冲突；尾延迟说的是流式断点，这里判的是收完之后的1 段整音。要压包就把同一套 Silero 换 int8 量化，模型不换。

语音输入只落在输入条自身的状态演化上，发送后的消息气泡、顶栏标题与标签卡片都不出现。音频编码统一采用 OGG 封装与 Opus 语音编码器，规格确立为48 千赫兹单声道、20 毫秒帧长与24 至 32 千比特每秒动态比特率，录制期间实时流式写入私有缓存；声波提取在采集期以100 毫秒能量窗口采样，结束时插值归一化为恒定100 根振幅峰值，每根柱量化至5 位整数并按位紧密排布为63 字节二进制数组，二进制完全兼容 Telegram 规范；消息实体由包含不可变标识、时间戳与投递状态的 Message 顶层类，以及承载本地沙箱路径、服务端地址、持续毫秒数与63 字节波形的 VoicePayload 载荷类构成，状态流转涵盖草稿、录制、锁定、试听与发送；安卓图元用微软 Fluent，iOS 图元用 SF Symbols，并精准映射 Telegram 官方原生物理动效、双层声波形变及垃圾桶动效，5 套真机视图闭环建立无缝双向交互。

采集是 48 kHz 单声道，MediaCodec 的 Opus 编码器逐包出流，自己写的 Ogg 封装把 OpusHead 与 OpusTags 一起写进页里，文件落在 cache/voice/{uuid}.ogg；同一路采集用33 抽头窗函数 sinc 降到 16 kHz、凑满20 毫秒1 帧继续喂实时会话，电平沿用原有分贝映射与 attack/release 2 档平滑。每100 毫秒记1 格 RMS，收尾归10%100 根、每根5 位紧凑压进63 字节，与 Telegram 的 waveform 同一套取法，输入条的时间轴就从这63 字节里取32 根画。暂停只停采集不封文件，返回这1 刻的波形与时长，恢复接回同一只文件继续写；试听走 MediaPlayer，进度80 毫秒读1 次；发送与作废都先封口再把文件删掉，缓存不留孤儿。真机验过设备产出的文件被 ffprobe 认成 ogg/opus、48 kHz、单声道、29 kb/s，暂停之后再续写仍是同一只文件。

## 画板与验证
